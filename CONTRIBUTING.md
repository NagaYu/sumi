# Contributing to Sumi

Thanks for looking. A few things that will save you time.

## Ground rules

These are enforced by the test suite, not just convention:

1. **Never commit real personal data.** Everything — names, addresses, numbers — is
   generated by seeded RNGs. `tests/test_synth.py` asserts that email domains are
   always reserved (`example.*`, `.test`, `.invalid`) and that check-digit
   identifiers are format-valid but value-invalid.
2. **Detection is never gated on a checksum.** Card- and My-Number-shaped strings
   are detected by format; validity goes into `meta["checksum_valid"]` and nothing
   more. Redaction must not leave something that looks like personal data.
3. **Every public function documents which claim it substantiates.** Its docstring
   must contain a `Claim:` line naming one or more of
   検出率 / 低誤検出 / CPU速度 / 可逆性 / 較正
   (detection rate / low false positives / CPU speed / reversibility / calibration).
   `tests/test_docstrings.py` enforces this.
4. **Offsets are Python character indices into NFKC-normalised text**, half-open
   `[start, end)`. Not bytes. Normalise once, on the base text, before inserting PII.
5. **Seeded RNG instances only** (`random.Random(seed)`, `np.random.default_rng(seed)`).
   Never mutate global random state.

## Language

Source-code docstrings and comments are written in Japanese — that is the project's
working language and the domain it targets. All *published* documentation (README,
model card, dataset card) and all user-facing runtime strings (CLI, Gradio app) are
in English. Please keep that split.

## Development

```bash
pip install -e ".[presidio,onnx,app,dev]"
python3 -m pytest
```

Every module also runs standalone as its own self-test:

```bash
python3 -m sumi.rules
python3 -m sumi.negatives
python3 -m sumi.mask
```

## Changing anything that affects the numbers

The README, model card and dataset card are **generated** from measurement files —
never edit them by hand, or your change will be overwritten. If you change the model,
the data or the rules, regenerate everything:

```bash
python3 benchmarks/run_benchmark.py --n-pos 250 --n-neg 250
python3 benchmarks/run_benchmark.py --pos-file ood.jsonl --tag ood --n-pos 100 --n-neg 100
python3 -m sumi.figures
python3 -m sumi.figures benchmarks/results/benchmark_ood.json _ood
python3 scripts/build_docs.py
```

Report both the in-distribution and the template-independent (OOD) numbers. The OOD
numbers are the honest ones; in-distribution results are inflated by template overlap
and must not be presented on their own.

## Adding a hard-negative kind

1. Add the kind to `NEGATIVE_KINDS` in `sumi/negatives.py`.
2. Write a `_gen_<kind>` method with at least ~25 distinct surface realisations.
3. Add a detection pattern to `_KIND_PATTERNS` so `classify_false_positive` can
   attribute errors to it — otherwise the closed loop cannot learn from it.
4. `python3 -m sumi.negatives` and check the histogram.
